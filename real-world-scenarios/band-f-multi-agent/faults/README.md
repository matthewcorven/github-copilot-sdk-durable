# Band F — fault evidence: who holds control after recovery

Five faults, run against **both** Band F variants, each writing one machine-readable result. Every
result answers the band's question — *which agent held control after recovery?* — from the state the
variant says control lives in, never from a log line.

```bash
./faults/run-all.sh                          # every fault, both variants, controls included (~20 min)
./faults/run-all.sh durable                  # one variant
./faults/run-all.sh --no-controls            # the five faults only
./faults/run-all.sh --faults store-outage    # one fault

./faults/kill-mid-delegation.sh --variant baseline
./faults/store-outage.sh --variant durable --fault-not-injected
```

Each script takes `--variant baseline|durable` and `--fault-not-injected`, which runs the same steps
with the injection removed and records it as a **control**. Every script exits `0` when it ran,
including when the variant lost work or could not recover — that is the observation, not a failure. A
non-zero exit is a harness error: a process that never came up, a state that never reached the
injection point, a pid that survived the kill.

## How control is attributed — and what is deliberately not used

This is the band's whole claim, and it is the easiest thing in the harness to get subtly wrong.

**The holder is read from committed state** (`lib/holder.py`):

| Variant | Source of the post-recovery holder |
| --- | --- |
| durable | `checkpoint.holder` of the `band-f.delegation` task record, in the JSONL store's last task record. The checkpoint is the variant's own single record of where the run is, so it is the variant's own answer. |
| baseline | the framework checkpoint the workflow is reconstructed from. The newest checkpoint's queued handoff names the agent about to run; failing that, the last handoff's `previousAgentId`; failing that, the last agent to speak in the checkpointed conversation. |

**What is not used, and why:**

- **The baseline's `control-transfer.jsonl`.** The port's own README says it is derived, not
  authoritative. Using it would answer "what did the port print" instead of "what does the state say".
  It appears in the baseline rows only where a *count* of turn ends is needed to locate an injection
  point, and the result says so where that happens.
- **A `holders:` summary line.** G2 (#207) found a `holders` filter that matched `"delegated"` and
  therefore silently dropped every turn a resume served as `"delegated-from-memo"`. F2's `verify` guards
  it now (check 4b). This harness does not read that summary for the assertion; it reads the store.
  `kill-mid-delegation` does print the reported holders in its evidence, cross-checked against the wire
  records, so the summary is *checked* rather than *trusted*.
- **Where the run ended.** `holderAtEnd` is the holder of the newest committed checkpoint once the run
  has stopped — a real reading, but not the question. On the durable variant the final `settle` commits
  `TaskCommit.Completed` **without** writing a coordinator checkpoint, so the newest checkpoint still
  names the specialist that produced the last turn; on the baseline the newest framework checkpoint after
  a finished run names whichever agent spoke last (the coordinator, for the closing courtesy turn). It is
  recorded because it is the value a careless harness would report as "who holds control", and it differs
  from the answer in exactly the way a reader has to be able to see. Where the two collapse to the same
  agent — the durable kill row, whose specialist produces and settles — the row says so rather than
  presenting three independent readings as corroboration.
- **A process's stdout.** Every injection point is reached by polling committed state, except the
  durable variant's own `--kill-after-*` seams, which announce a pid *after* the commit they name has
  returned. A pid is not a holder, so that is the one thing read from a line.

## Why the baseline's rows look the way they do

The baseline is faulted on the same axis, and F1 built `run`/`resume` modes for exactly this. What the
faults found is not that the baseline cannot be faulted — it can, and `competing-managers` and
`store-outage` both complete for it — but that **its recovery cannot finish**:

```
[control] resumed with return_agent holding control; skipping 2 completed turn(s)
- User: Please also process a refund for order 1234.
[control] handoff requested by triage_agent (handoff_to_1)
[control] workflow error: System.InvalidOperationException: Expected exactly one update for key 'SharedState'.
```

Every resume of a workflow that still has work outstanding aborts inside `Microsoft.Agents.AI.Workflows`
with `Expected exactly one update for key 'SharedState'`, leaves a newer checkpoint behind, and aborts
there too. `recover_variant` in `lib/common.sh` therefore tries a bounded number of processes and records
every abort; a recovery that needed two processes says so. A fault that depends on the recovery
*finishing* — `duplicate-delivery` — is recorded as `not exercised` with that reason rather than a count
from an aborted run.

That is the honest comparison: the baseline's checkpoint mechanism is a position, and restoring a
position into a running graph is where it stops. It is not a durability win for this variant to say so;
it is what the fault found.

## The injection points

A fault script never sleeps and hopes.

- **durable**: `kill-mid-delegation`, `duplicate-delivery` and `restart-after-checkpoint` use the
  variant's own seams (`--kill-in-turn`, `--kill-after-delegating`, `--kill-after-routing`), which print
  `[seam] ready-to-kill pid=<n>` once the commit has returned. `competing-managers` and `store-outage`
  poll the store's `checkpoint.holder`.
- **baseline**: every fault polls the framework checkpoint. `holder_json` reads it, so the same rule
  that attributes control also says when the fault is due.

The kill is always the **application's own pid**, found by asking which process holds the store file
open (`lsof` on `store.jsonl.lock` for the durable variant, `index.jsonl` for the baseline), never
`$!`. Both variants' `run.sh` are wrappers that start the app and wait for it, so killing the wrapper
would leave the app reparented to pid 1 — out of reach and still holding the store lock. Both kill and
stop are confirmed: the script waits for the pid to be gone and fails the run if it survives.

## The before/after controls

Each control is the same script with the injection removed. What the pair is for:

- `kill-mid-delegation` control leaves the run alone: it finishes in one process, so the second process
  in the fault run belongs to the kill.
- `restart-after-checkpoint` control stops one commit earlier, where the coordinator still holds the
  turn. The two rows land at two different holders, which is what shows the restart reads the commit
  rather than assuming a holder. (For the baseline, both rows fail, and the *holders* still differ:
  the fault stops after the delegation and the control before it.)
- `duplicate-delivery` control delivers once: turn 3 commits **one** output. The fault's per-turn count
  is what the pair turns on — a second output version for the re-delivered turn, or a reuse record,
  would mean the tool ran twice for it. The whole-run multiset is recorded but decides nothing:
  `return_agent` answers turn 0 as well, so its result appears twice in the control too.
- `competing-managers` control starts one manager, so the refusal belongs to the second.
- `store-outage` control moves nothing, so the split store belongs to the outage.

### `durable / duplicate-delivery`: what the row is, and what it is not

The row reads **not doubled**, and that verdict rests entirely on the per-turn count: turn 3 committed
one output version and nothing was reused, so the tool did not run a second time for the re-delivered
turn.

It is **not a durability win.** What stopped the second run was finding the turn's output already
committed — not an identity for the request. This variant memoizes a routing decision it has not yet
acted on; it has no memo for an output a process has already consumed, and nothing in this run showed
it would deduplicate a delivery it had no record of. The per-turn count says the work happened once
here; it does not say the variant can tell that a request is a repeat.

The script also delivers the request a third time, to the finished run. That attempt is recorded, and it
is evidence of one thing only: **a finished run is a no-op.** It is not the deduplication finding. The
finding is the per-turn count above; the third delivery is a separate observation about a run that had
already ended, and a reader who takes it as the claim has read it backwards.

`lib/summarise.py` flags any pair whose outcome *and* holder match, because such a control proves
nothing. Where it does — the durable `restart-after-checkpoint` pair, both landing at `refund_agent` —
the rows genuinely differ in *where* they stopped: the control stopped at phase `route` and the fault at
`specialist`, and the evidence for each says which. It is reported rather than hidden.

## Re-runnable

Every run gets its own directory under `$FAULTS_SCRATCH` (default `.scratch/band-f-faults/`), its own
state beneath it, and its own build output. A cleanup trap reaps the application, its wrapper, and
anything else whose command line names the run directory, by pid — then removes the directory unless
`KEEP=1`. A run that fails leaves no process and no store behind; a second run starts from nothing.

The store lives at `<rundir>/state/` rather than at `<rundir>` itself, so each variant's own scratch
guard sees a path it created and a fault can never be handed a directory the variant would refuse.
