# Band D (D4) — fault evidence: platform recovery vs application recovery

Six faults, run against the two Durable positions and the baseline they compare against. Every result
carries **two blocks that are never merged**: `platform` says what Foundry did, `application` says what
this repository's code did. That split is the whole subject of the issue, so the format enforces it
rather than trusting a reader to keep it.

**Nothing in this directory provisioned anything.** No Foundry deployment, no Azure resource, no model
call, no credential. Every result therefore records `platform.live_foundry_called: false`, and the four
platform behaviours D1 measured are quoted from its captures as
**`documented, not exercised here`** — never upgraded to "reproduced" because a local analogue looked
similar.

```bash
./faults/run-all.sh                        # the whole matrix, into results/ (~15 min)
./faults/run-all.sh durable-outside        # one variant, into a scratch directory
./faults/run-all.sh --no-controls          # faults only, into a scratch directory
KEEP=1 ./faults/run-all.sh ...             # keep every run directory, container and volume

./faults/client-dies-mid-run.sh  --variant baseline
./faults/container-restart.sh    --variant durable-inside
./faults/agent-call-failure.sh   --variant durable-outside --fault-not-injected
```

Each script takes `--variant` and `--fault-not-injected`. A script exits `0` when it ran, **including
when the application lost work** — a lost run is the observation. A non-zero exit is a harness error: a
container that never started, a marker that never appeared, a kill that could not be aimed at the
process it was meant to hit.

## The distinction this band exists for

| Observation | Whose | Where it is recorded |
| --- | --- | --- |
| "the session came back" | **the platform's** | `platform.behaviours[]`, from D1's captures |
| "our step did not re-run and the side effect did not repeat" | **the application's** | `application.observations`, from this run's call counts |

`lib/result.py` refuses a result that claims `reproduced here` for a platform behaviour while
`platform.live_foundry_called` is false, and refuses one with an outcome but no application
observation. A result that could blur the two cannot be written.

## The matrix

Generated by `lib/summarise.py` from `results/*/*.json`; `results/summary.txt` is its output. Nothing
in this table is typed by hand.

The `baseline` column is D1's design — the accelerator's two hosted agents invoked over the Responses
protocol — driven by a client, because that is all it has. `durable-inside` is D2's own container
(`agent/` + `lib/py`, built from D2's own Dockerfile). `durable-outside` is D3's published orchestrator.

| Fault | Injection | baseline | durable-inside | durable-outside |
| --- | --- | --- | --- | --- |
| `client-dies-mid-run` | `kill -9` of the driving client inside a held call | **an already-accepted call is paid for twice** | `not exercised` — no client of its own | **the unfinished step is re-called; nothing completed is repeated** |
| `container-restart` | `docker stop` **and start** on a real container over one session volume | **cold start; nothing survives** (it has no container) | **the parked approval and its deadline survive byte-identically** | `not exercised` — its restart is its client's death |
| `duplicate-delivery` | the same input / the same decision, twice | **both steps applied twice; nothing refused** | **one decision applied once; the second delivery woke nothing** | `not exercised` — its gate refuses by construction |
| `concurrent-clients` | two live clients over one run | **both applied both steps; no conflict detected** | **the second refused by the store's file lock** | **the second refused by the store's file lock** |
| `store-outage` | the store made unwritable by the OS, then left in place | **failed loudly; nothing kept** (the analogue: the service withdrawn) | **failed closed; the store's bytes unchanged, and readable again afterwards** | **the commit was refused; the run did not advance** |
| `agent-call-failure` | the **last** call answers 503, then the failure is lifted | **the failed call retried; the earlier step skipped by a file check** | `not exercised` — no application-issued call | **the failure settled the run; a separate memo arm shows +0 calls on a re-entered phase** |

**Four cells are `not exercised`**, and each says which variant and why in its own result file: D2 has no
client to kill (`client-dies-mid-run`) and no application-issued call to fail (`agent-call-failure`); D3's
restart *is* the death of its client (`container-restart`), and its gate refuses a second answer by
construction (`duplicate-delivery`). That is a statement about the variant's shape, not a gap in the
harness. Each of the four also has a `-control` result, which records *why no control exists* for a fault
that was never injected — it is a control for the cell, not a fifth non-exercised cell, and the counts in
`results/run-status.txt` are only legible with that distinction: 36 results = 14 exercised runs + 14
controls + 4 non-exercised cells + 4 controls-for-a-cell-that-cannot-be-run.

## The headline: the four faults worth reading

### `client-dies-mid-run` — what a memo does and does not cover

The injection is a real in-flight call, not a sleep: `lib/fake_foundry.py` holds the coverage
response, so the client is killed inside `InvokeAsync` with the request already on the service's log.

| Variant | coverage calls before the kill | coverage calls in total | reading |
| --- | --- | --- | --- |
| baseline | 1 | 2 | the killed step was paid for twice |
| durable-outside | 1 | 2 | **also twice** — and that is the finding |

D3's store holds the task, its checkpoint and its memos, but the interrupted step had **not returned**,
so it has no memo. A memo covers a completed call; it cannot cover a call that never finished. What D3
does protect is measured in `agent-call-failure`'s memo arm and in D3's own kill-at-gate evidence (+0
calls), and those measure a different thing: a phase re-entered *after* its memo was written.

Stated plainly, because it is the kind of thing a band like this could quietly get wrong: **a kill
inside a call repeats that call, in every column.** Durability moves the cost from "repeat everything"
to "repeat the one step that was in flight".

### `container-restart` — the one the band asks for by name

A real container commits the assessment and a parked approval, then is stopped with SIGTERM while a
later step is held open. A **new** container reads the same session volume:

```
deadline before restart   1794920094.0650766
deadline after restart    1794920094.0650766      identical: yes
task                       t4, WAITING on external:approval/PA-D4-0001
after a third process delivered the decision:
  settled                 completed
  work state phase        decided, by 'D4 harness reviewer'
```

The interesting part is the digits, not the outcome: the *same* instant to the microsecond, not "24
hours from now, again". The volume is a named Docker volume and it has to be — `flock` over a bind mount is local to
each container, so two containers over one host directory both believe they hold the lock. The harness's
first version used a directory, and the `concurrent-clients` row is how that was caught: the second
client was **not** refused, which is not what the layer does. The volume is the fix and the result says
so.

### `concurrent-clients` — the lock is the operating system's

| Variant | second client | evidence |
| --- | --- | --- |
| baseline | no refusal, both ran | coverage 2, synthesis 2 |
| durable-inside | exit 1, `already open in another process (pid=1 …)` | work state holds **1** version, not 2 |
| durable-outside | exit 134, `is already open in another process` | the second process wrote nothing |

For D2 the refusal is `flock` on the store's sidecar; for D3 it is file sharing on the lock file. Neither
variant checks whether another process is running. That is the point: the safety is in the storage, not
in an application-level flag someone has to remember to set.

### `agent-call-failure` — the fault as aimed, and the second injection it needed

The fault makes the **last** call fail, so every earlier step is a candidate for a re-call. What
happened is worth recording exactly: D3 retries a 5xx four times, then the phase throws and the task
settles **failed**. The resume then reports `already finished; nothing to do` — `+0` calls, but not
because of a memo. The run was terminal.

So the result carries a second arm, on a fresh store, against D3's own `STOP_AFTER_COVERAGE=stuck` seam:
coverage's memo is written, the checkpoint does not advance, the process stops. The next process
re-enters `coverage` — the only state in which "+0 calls" means "the memo was used" rather than "there
was nothing left to do":

```
memo arm:  coverage calls before resume 2, after 2, repeated 0
           resume reported a memo hit: yes
           phase re-entered: coverage
```

The first arm's limitation is written into its own result rather than smoothed into the second's
vocabulary.

## The before/after controls

Each control runs the same steps with the injection removed. The outcomes are named `control: …` so a
control is never read as the fault's.

Two controls are worth naming because their *shape* differs from the rest: `durable-inside` /
`store-outage` has no deletion in it at all — the volume is mounted read-only, so the control differs from
the fault by the mount and by nothing else — and the four controls for a cell a variant cannot have say so
in their own outcome rather than borrowing `control: …` from a run that happened.

The row that does not flip, and why it is stated rather than hidden: **`baseline` / `container-restart`
control`. The baseline has no container, so the control is a client restart with no kill — and it
records a *completed* run against the fault row's cold start. That does flip. What does **not** flip is
`baseline` / `client-dies-mid-run`: its control also completes, but the fault row's doubling belongs to
the missing progress record rather than to the kill, which is why the row is worded as "paid for twice"
and not "the kill doubled it".

## What the platform did, in one table

`lib/platform.py` carries all four behaviours and every result embeds it. The statuses are exactly two,
and `lib/result.py` refuses a third.

| Behaviour | Status here | Source |
| --- | --- | --- |
| Session persistence — 30 days, sliding on activity | `documented, not exercised here` | `../evidence/platform-behaviour.md` §1, `../evidence/session-resume/` |
| Idle timeout — 900 s default, deprovisions compute and saves state | `documented, not exercised here` | `../evidence/platform-behaviour.md` §2 |
| Foreground response cancelled when the client goes | `documented, not exercised here` | `../evidence/platform-behaviour.md` §3; response `status: cancelled`, `background: false` |
| No replay for foreground; background re-entry starts at the handler's beginning | `documented, not exercised here` | `../evidence/platform-behaviour.md` §4 |

**Why none of them was reproduced.** D1 tore its deployment down; nothing in this band is allowed to
provision or spend. A local container that survives a local `docker stop` is *evidence about Docker*,
and calling it "the platform's session persisted" would be exactly the misattribution this issue was
filed to prevent. `evidence/attribution.md` works through each of the four and what a future run with a
deployment would have to show to move one to `reproduced here`.

## What each result is, and is not

Every result carries a `harness` block that says where each column ran and a `platform` note that says
what the stand-in is not:

- **`lib/fake_foundry.py`** serves D3's two endpoints and appends one line per request to
  `service/calls.jsonl`. A call count is `len()` of that list, and no participant in the run can write to
  it — the same discipline D3 used with the platform's own response list, over a list this process owns.
  It is **not Foundry** and recovers nothing.
- **`lib/baseline_driver.py`** is the accelerator's decision path as a client, without the platform.
  D1's honest baseline is that the platform owns session and transcript; this driver therefore owns
  nothing, which is what the baseline rows measure.
- **D2's image** is built from D2's own `agent/` and `lib/py` with D2's own Dockerfile, assembled the way
  `infra/deploy.sh` assembles it. The code that survives a restart is the scenario's.
- **D3's binary** is `dotnet publish`ed so the PID the shell starts is the application, not a `dotnet`
  host in front of it. `dotnet run` would have made every `kill -9` land on the wrapper.

Two things in the envelope exist so a result can be checked later rather than believed:

- **`harness.docker` names the container a result actually used**, read from the daemon when the image is
  built or found — client and server versions, the image tag and its digest — and says plainly when a
  fault used no container. A run that ran in Docker and a run that did not are therefore distinguishable
  from the file alone.
- **`harness.command` is the invocation that produced that file**, so a control carries
  `--fault-not-injected` and is never read as its fault's row.
- **Paths are normalised**: a quoted application message can contain the absolute path the run happened
  in, and a checked-in result must not name one reader's checkout. `<repo>` and `$FAULTS_SCRATCH` replace
  the repository root and the scratch root; `harness.paths_normalised` records the substitution, so the
  rewrite is visible instead of silent.

## Not proven here

- **That a real Foundry session outlives a real container restart.** Documented, observed once by D1, not
  reproduced. A deployment is the only way to move that row, and this band had none.
- **That the platform's own concurrency is serialised.** Two clients against one `agent_session_id` is not
  something this harness can reach; `concurrent-clients` measures two processes over one store.
- **That one overlap window is representative.** The windows were chosen, not sampled.
- **Model-call cost.** The stand-in serves fixed answers, so a "call" here is a request, not a billed
  inference. The counts compare designs; they are not cost evidence.
- **`agent-call-failure` on a non-terminal failure path.** The 5xx D3 produces is terminal. A failure
  that left the task running would have let the first arm show a memo hit directly; that path is not
  reachable through D3's current retry-and-throw, and the memo arm is the substitute.
- **That the result guard is complete.** `lib/test_result.py` proves the refusals `lib/result.py`
  actually makes — eighteen cases, one of which is the exact misattribution this band exists to prevent,
  and three of which pin the path normalisation and the control's command line —
  but it cannot prove there is no *other* way for a result to blur the two blocks. What it does prove is
  that the guard is not decorative: `run-all.sh` runs it before writing any result, and a refusal is an
  exit status with no file written.

## How many runs, and at which commit

`results/run-status.txt` is the record, not the prose here: **36 entries**, one per fault, control and
recorded-not-exercised cell, every one exit `0`, produced by one invocation of `./faults/run-all.sh`.
The commit each result was measured at is in its own `harness.commit`, so a reader does not have to
trust this paragraph for it.

## Layout

```
faults/
  run-all.sh                    sequence every fault, then render the summary
  client-dies-mid-run.sh        one script per fault; all take --variant and --fault-not-injected
  container-restart.sh
  duplicate-delivery.sh
  concurrent-clients.sh
  store-outage.sh
  agent-call-failure.sh
  lib/common.sh                 scratch dir, service, variants, volumes, cleanup
  lib/fake_foundry.py           the stand-in data plane; its request log is the call count
  lib/baseline_driver.py        D1's decision path as a client, with a hold seam
  lib/fence.py                  a standalone reader of the store's shape; not called by the sweep
  lib/platform.py               the four documented behaviours, one place
  lib/result.py                 writes a result and refuses a blurred one
  lib/not_exercised.sh          records a variant's "cannot have this fault" as a result
  lib/summarise.py              renders results/summary.txt; fails on a missing result
  results/                      checked-in results and the rendered summary
```

Nothing is left behind: `lib/common.sh`'s trap reaps every process, container and volume it started,
and `run-all.sh` reads `results/run-status.txt` rather than the absence of an error message.
