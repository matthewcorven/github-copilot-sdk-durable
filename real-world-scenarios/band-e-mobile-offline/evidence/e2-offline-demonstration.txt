Three things in that trace are the demonstration:

- **the prepare changed nothing.** 878,065,731 B / 11 files before and after, with the network off:
  13.3 s of model *load*, zero bytes fetched. (The two later loads in this session were 7.9 s; the
  13.3 s one is the first load after the process started and the OS page cache was cold.)
- **the message count grows 2 -> 4 -> 6.** The whole transcript is re-sent every turn because the
  SDK keeps none. Turn 2 knows about turn 1 only because the store holds it.
- **every turn committed a document revision.** rev 1 -> rev 2 -> rev 3, each with the entry id that
  produced it, in the store.

What this proves, and what it does not
--------------------------------------

Proven: the document the app shows after the kill is the document the model wrote before it, byte for
byte, restored from a file the new process opened. The transcript has four turns because the store had
three and turn 4 was appended to them; the model was given eight messages because the store could
supply six.

Not proven, and not claimed: that the model *edited* the document surgically. Read the body above. It
is a rewritten document, 1269 characters every turn, not an in-place edit of a section — a 0.5B model
regenerates rather than patches, and it did not add the "On-call engineer: Dana" line to what was
there so much as produce a new body in which "Dana" appears once in a closing note. The demonstration's
requirement is that *a document the agent edits across turns* stays intact across a kill; that is what
the screenshots and the hashes show. The model's writing quality is a measured cost, recorded in
evidence/e2-model-protocol.txt and priced in the README's resource table.

A second honest observation: turns 2, 3 and 4 all landed on 1269 characters. That is the model
converging on a similar length under the 220-token cap, not the store returning a stale value: the
version count rises 34 -> 39 across those commits, each revision has its own entry id and sequence,
and the revision-1 body (1248 chars, the turn-1 document) is a different text from the revision-4 body
quoted in section 8.

===============================================================================
9. What this capture does not show
===============================================================================

- **The task layer in depth.** A durable task per turn exists, is committed before the model is
  called, and is closed in the transaction that stores the reply — section 4 shows the checkpoint
  lines, and evidence/e2-store-on-device.txt shows a completed task's record. There is no multi-phase
  task machine, and the README says why rather than implying there is.
- **A phone.** Every number is this emulator.
- **The download's own trace.** The harness only began writing per-step traces after the download
  completed; evidence/e2-resources.txt says so and uses the screen's own figure for it.
