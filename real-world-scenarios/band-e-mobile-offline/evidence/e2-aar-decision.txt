Band E / issue #166 — the AAR decision: why this device runs the embedded SDK
Captured 2026-11-25 on AVD band-e-api36-playstore-arm64, arm64-v8a, API 36.

DECISION-bridge.md 2 chose IPC, with embedded as "a documented, fetchable fallback", and named the
triggers that would re-open it. This file is the evidence for taking that fallback on this device.
DECISION-bridge.md 6 is the record; this is the raw material.

===============================================================================
1. The trigger: the IPC companion app is not installable here
===============================================================================

Google Play on this emulator reports, for com.microsoft.foundry.app:

  Foundry Local isn't compatible with this version

and the package the IPC AAR queries for, com.microsoft.foundrylocal.app, is not installed:

$ adb shell pm list packages | grep -i foundry
(no output)

E1 established the same thing from the other direction on the physical device: no APK is published
for the companion app, so Play is its only source (evidence/e1-physical-device.txt). On this emulator
Play refuses it outright. The IPC path cannot start here — not "started and failed", but "cannot be
entered at all", because FoundryLocalManager.create checks for a service app that does not exist.

===============================================================================
4. How the embedded manager registers itself
===============================================================================

The embedded AAR's manifest declares a ContentProvider that registers the manager factory at process
start, so FoundryLocalManager.create works with no companion app:

$ unzip -p libs/foundry-local-embedded-sdk-0.1.6.aar AndroidManifest.xml
  <provider
      android:name="com.microsoft.foundrylocal.embedded.EmbeddedSdkInitProvider"
      android:authorities="${applicationId}.foundrylocal-embedded-init"
      android:exported="false"
      android:initOrder="50" />

The manifest comment above it in the AAR states that embedded uses initOrder=50 and IPC initOrder=100
"so when both SDKs are on the classpath the embedded factory overwrites IPC". That is why exactly one
AAR may be referenced: with both, the winner is an init-order tie-break rather than a decision, and a
demonstration should not rest on one.

6. What the fallback costs
===============================================================================

- app size: 84 975 920 B (81.0 MiB) for the signed APK of the final build
  (`sha256:86e58d9daf5edb1a0d458434fc18a096b285fbd5d28a565bacd6901951e7534c`), because the engine
  ships in the app (DECISION-bridge.md 2's table puts the IPC AAR at 441 KB and the embedded at
  44 MB; the APK cost is the native libraries, listed above).
- no process isolation: a native crash in the engine takes the app down. This variant's subject is a
  store that survives the process, so that liability is acceptable here in a way DECISION-bridge.md 2
  argued it was not for the default path.
- model management is the app's: the cache is app-private (files/models_cache) and removed with the
  app. The IPC mode shares a service-managed cache between clients; embedded does not.
- `isConnected` is not applicable: the SDK's own mode table says connection loss is "Not applicable"
  in embedded mode. A turn that completes here is therefore evidence that no connection was needed,
  which is stronger for this variant than a healthy connection would have been.
